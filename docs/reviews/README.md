## 执行摘要

Andromeda 的**工程基本功很强**：crate 分层严格无环、`unsafe_code = forbid` + clippy pedantic、109 个测试全绿且含大量对抗性/回归用例、存储层崩溃安全与乐观并发设计正确、OS 交付流水线以证据为中心且安全边界多重冗余。核心契约层（`andromeda-core`）尤其成熟——`IsolationLevel::satisfies` 刻意用非线性矩阵而非 `Ord`，是全仓最深思熟虑的设计。

真正的风险**不在"有 bug"，而在"契约形状"与"信任边界"**——这些一旦被即将落地的 executor 当真消费，回改代价很高。多个维度独立指向同一批结构性问题，构成下方"跨维度主线"。

## 跨维度主线（多个 agent 独立印证）

这些问题被 ≥2 个独立评审各自发现，可信度最高，应优先处理：

### A. taskd 的信任边界与"Host 校验=保护"的错误声称
*(安全 #2、架构 #6、文档 #1 — 三个 agent 独立命中同一处)*
`taskd` 无鉴权；Host 头校验只防浏览器 DNS-rebinding，对非 loopback 绑定**毫无保护**（远程客户端可自带 `Host: localhost` 通过）。而 `docs/development/task-control-plane.md` 曾声称"绑定非 loopback 会全部被拒——防裸奔"，与代码及本仓库另两处更诚实的文档矛盾。
→ **本轮已修**该文档过度声称（见下"本轮附带修复"）。代码侧仍建议：systemd 加 `IPAddressAllow=localhost`/`IPAddressDeny=any` 做内核级回环强制；executor 落地前引入本地鉴权（`SO_PEERCRED`/UNIX socket）。

### B. `evaluate` 的隔离粒度与非线性 satisfies 矩阵冲突 → 混合风险计划不可执行
*(架构 #1，安全 #3 与之相关)*
`TaskService::evaluate` 用**单一 task 级** `IsolationLevel` 评估整个 plan，而 `satisfies` 是非线性的：不存在任何单一隔离同时满足 `MicroVm`（L2）与 `Brokered`（L3）。因此"microVM 解析 + broker 外发"这类最典型的混合计划在任何隔离取值下都必有一侧 Deny——且创建时 `plan_fully_granted` 用逐 action 隔离、evaluate 时切回全局单标量，两套模型自相矛盾。这是 executor 落地前**最该先修的契约形状**（`EvaluationRequest` 一旦被消费就难改）。

### C. 授权/审批闭环缺失
*(架构 #2、安全 #3)*
`AwaitingApproval` 无补授权入口（capability 只能创建时随请求提供），且 `transition` 不做策略复检——任意本地进程可把 `AwaitingApproval → Ready → Running`，绕过它所代表的审批。`Ready ≠ 已授权` 只靠文档约定，无机制护栏。

### D. 存储 O(n²) 与双份 plan 校验
*(架构 #4/#7、代码 #2/#3 + 可维护性 #1)*
每个 revision 文件内嵌全量事件历史、只增不减、`get` 全目录扫描 → 存储与列举皆 O(n²)（已文档化 compaction TODO，但未提单文件二次膨胀与全目录扫描）。同时 `ActionPlan::validate`（core，Kahn）与 `validate_plan`（runtime，DFS）是同一不变量的**两套实现、两套错误枚举、两种环检测算法**，core 那套在生产路径是死代码，长期必然漂移。

### E. HCM 只验一致性/新鲜度、不验真实性
*(安全 #1，已实机复现)*
伪造一份含任意 `sha256`、任意"passed"证据的清单即可让 `andromeda hardware check` 判定 `certified`（退出码 0）；`ArtifactPin.signing_key_id` 被解析但从不使用。今日 HCM 判定仅"咨询性"（安装器 preflight 用镜像 label），但 `hardware check` 的退出码显然为脚本门控设计，一旦用于放行即升级为严重。需 detached 签名 + 制品哈希核对。

### F. E2E 无法捕获 bootc 原始 stderr（可观测性缺口）
*(OS #1，本轮真实踩到)*
本轮 os-e2e 曾因 `bootc install to-filesystem exited with status 1` 失败，root-cause 极难定位——因为 `test-install.sh` 的失败路径在收割 ESP 诊断**之前**就 `exit`，且 harness 未对 bootc 子进程输出做一等采集，上传证据只留下 anaconda 包装后的"status 1"。这是决定 MTTR 的一等缺口，修复成本低（收割顺序前移 + 采 Payloads 模块 journal）。

## 平台级不一致：Support Tier 阶梯
*(文档 #2/#3)*
`SupportTier` 在战略文档（`Reference` = 最高 Tier 4）与代码/开发文档（`Reference` = 次低，`Blocked < Community < Reference < Supported < Certified`）中方向相反，`Reference` 一词占据阶梯两端。需选定单一 source of truth（推荐以代码语义为准、给战略文档的"OEM 参考线"改名），并加 CI 断言校验 `model.rs` 声明顺序 == JSON schema enum 顺序。

## 建议的处理优先级

1. **【executor 落地前必须】** 主线 B（evaluate 隔离契约）、C（授权闭环）、A 的代码侧（本地鉴权 + 内核级回环）。这些是"契约形状"，越晚改越贵。
2. **【尽快】** 主线 F（bootc stderr 可观测性，成本低收益高）、E（HCM 签名，或先在文档声明"check 结果不可作信任门控"）、代码 #1（不可信输入加 `deny_unknown_fields`）。
3. **【清理/一致性】** 主线 D（存储 compaction + 合并双 plan 校验）、Support Tier 阶梯统一、文档 #4/#5（失效脚本引用、过时 marker 列表）。
4. **【纵深加固】** macOS 大小写不敏感 deny-root、供应链 digest+签名固定、systemd 额外 sandbox 项。
