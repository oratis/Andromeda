# 四项整改设计的对抗评审（全部被否）

> 日期：2026-08-02
>
> 背景：[三大产品目标对齐评审](./ai-native-goals-review.md) §5 列出四项待办工程。
> 本轮为每项产出一份落地设计，再由**独立 agent 逐份对抗性复核**（任务是"驳倒它"，
> 而非"确认它"），复核者读真实仓库、核对包名/crate API/文件路径是否真实存在。
>
> **结果：四份设计全部被判 `needs-redesign`。** 本文记录被驳倒的内容与
> **任何重做必须满足的约束**，使下一轮不再重犯。
>
> 这份文档存在的意义：**被否的设计不落地，但被否的原因必须留存。** 否则下一位
> （人或 agent）会以同样的思路重新提出同样的方案。

## 0. 为什么值得单独记一篇

四份设计都写得像样：有取舍、有依据、有代码片段。但对抗复核在其中找到了
**26 条致命缺陷**，其中至少三条会造成真实损害：

| 缺陷 | 后果 |
|---|---|
| capability 签名设计把密钥目录设在 `/var/lib/andromeda`（0700 root:root），而服务以 `DynamicUser`/专用用户运行 | **taskd 启动即失败** |
| 供应链设计把 `containers/policy.json` 装进镜像 | **bootc 更新被签名策略拒绝，系统失去更新能力** |
| HCM 撤销列表未验签即可提升/限制等级 | **fail-open**：一个未认证文件影响信任判定 |

若把"设计看起来合理"当作"可以实现"，这三条会分别表现为：装完不开机、装完不能更新、
以及一个看起来更安全实则更弱的信任模型。**对抗复核的成本远低于其中任何一条的代价。**

## 1. 能力签发与本地鉴权（capability-auth）

**设计要点**：`Capability` 增加规范字节编码；线上/持久化类型改为不可选签名的
`SignedCapability`；新建 `andromeda-signing` crate（Ed25519）；taskd 只做验证不持私钥；
UNIX socket + `SO_PEERCRED` / TCP + owner-only token 双路径。

**方向是对的**，但实现细节被驳倒：

### 致命

1. **启动即失败**：keyring 放在 `/var/lib/andromeda/keys`，但该目录在两处独立位置被创建为
   `0700 root:root`，而服务不是以 root 运行。
2. **签发路径同样不可用**：`UMask=0077` 使 `keys init` 写出的策略文件为 `0600 root:root`，
   本该签发的用户组读不到。
3. **依赖前提是错的**：设计以"引入 Ed25519 是重大取舍"立论，但
   `ed25519-dalek 2.2.0` **已经是工作区依赖**（`andromeda-hardware` 已声明）。
   整个"选型论证"因此建立在错误事实上。
4. **供应链无谓膨胀**：新增 `getrandom 0.3.4` 会让锁文件里出现**第三个** getrandom 大版本
   （已有 0.2.17 与 0.4.3）。`base64` 同样多余——仓库对同类对象一律用 hex。
5. **核心保证未被强制**：`AuthConfig::resolve` 校验的是**配置**而非 serve 接线，
   匿名监听在类型上仍可表示；UNIX 路径下 token 变为可选，实际部署的单元又设成
   "只记录 uid、不做授权判定"，**镜像里的行为与设计摘要不符**。
6. **新增本地 DoS**：对**无界**的调用方 capability 向量做强制 Ed25519 验证。
   （此条已单独修复，见 PR"Bound the capabilities a task may hold"。）

### 重做必须满足

- 密钥目录的属主/权限与服务运行身份**在同一处定义**，并有断言；
- 认证保证要在 **serve 接线**上不可绕过，而不是在配置校验里；
- 先核对 `Cargo.toml`/`Cargo.lock` 现状再论证依赖取舍；
- 任何强制密码学校验的输入必须**先有长度上界**；
- 必须同步更新 [威胁模型](../andromeda-threat-model.md) §4.2——该节把这三项列为
  executor 的阻塞前置项，是**明文的合并门槛**。

## 2. HCM v3 表达力（hcm-v3）

**设计要点**：cohort 选择器（board/SKU/固件区间/ACPI/DT）、排除选择器、
`degraded`/`unknown` 证据、撤销列表。

### 致命

1. **前提已过时**：设计称"CLI 无法传入 keyring"，但该能力在本轮已经落地
   （见 PR "Gate hardware check on manifest authenticity"）。设计针对的是一个已消失的缺口。
2. **会作废所有现存签名**：新规范化方案默认套用到没有 `canon` 字段的旧签名上，
   而现有 `ManifestSignature` 只有两个字段——**方向刚好反了**。
3. **"零签名扰动"是假的**：`#[serde(alias)]` 只保住**解析**，保不住**签名字节**；
   规范化会重新序列化类型化模型，旧清单的签名随即失效。
4. **撤销是 fail-open**：`evaluate_revocations` 不验签、不接收 keyring，
   一个**仅仅存在**的未认证文件即可影响等级判定。这比没有撤销更危险。
5. **`certified_capabilities` + `required: false` 复现了它要防的洗白**：
   只拒绝缺项与 `Unknown`，于是声明能力却给一条非必需的降级证据即可蒙混。
6. **`evidence[]` 未约束重复 `capability`**：`.find()` 取第一条，重复项可绕过检查。
7. **`FirmwareRange` 既无 `min` 也无 `max` 时匹配一切**可解析版本。
8. **cohort 精确性判定不精确**：`{"bus":"pci"}` 能匹配任何有 PCI 设备的机器，却被判为精确。
9. 文档化 `pub fn` 缺 `# Errors` → **clippy pedantic 直接失败**。

### 重做必须满足

- 规范化版本必须**显式**、默认指向**旧行为**，新行为只在新清单上启用；
- 撤销列表必须与清单同等验签，未验签一律**忽略而非采信**；
- 排除选择器**不得**计入"判别性"，否则只写 exclude 的选择器会匹配一切；
- 任何"精确 cohort"判定要按**字段语义**而非**字段是否存在**；
- 先确认当前 CLI/库能力，避免为已修复的问题重新设计。

## 3. OS 可靠性与 CI（os-reliability）

**设计要点**：greenboot 健康门控与自动回滚、断电故障注入、基础镜像 digest 固定与签名策略、
CI 超时预算与 `/dev/kvm` 断言、nightly。

### 致命

1. **回滚身份判断错误**：`ostree=` karg 形如
   `/ostree/boot.<bootversion>/<osname>/<bootcsum>/<bootserial>`，其中 `<bootversion>`
   在**每次** `ostree_sysroot_write_deployments` 时 0↔1 翻转——同一个物理 deployment
   在不同 bootloader 代次下字符串**不同**，据此判断"是否回滚成功"必然误判。
2. **断电注入是表演**：计时从 host 观察到 `ARMED` 开始、到下次启动**最末尾**的
   `RECOVERED_OK` 结束，测的是错误区间，因此注入点分布与真实更新窗口无关——
   **正是该设计声称要消除的失效模式**。
3. **超时预算超出约 3 倍**：声明 45 分钟，内部 deadline 累计 ≥145 分钟，
   且其自身的预算守卫会算出矛盾。
4. **签名策略无法"默认关闭"**：只有一条无条件 `COPY os/files/ /`，build ARG 无法排除子路径，
   因此 `etc/containers/policy.json` **必然**被装入；而仓库自己的 runbook 明文
   **禁止**这样做——装上即 **bootc 更新被拒**。
5. **构建当场失败**：`os/base-image.env` 用字面占位 `sha256:0000...`，
   三处 `podman build` 立刻 `manifest unknown`。
6. **必需健康门重新引入它要防的离线回滚**：把"存在 failed unit"判红，
   而离线机器上 `NetworkManager-wait-online.service` 本就会超时失败 →
   **离线笔记本被自动回滚**。
7. **发布 `:edge` 反而是安全倒退**：今天该 tag 悬空，远程 `bootc upgrade`
   **fail-closed**；在强制签名落地前把它变成可写的活 tag，等于把一个安全默认换成风险。
8. **GRUB 计数器安全网静默可选**：以 `if [ -f ]` 软跳过缺失单元，
   而这些单元historically 在独立子包中——最该兜底的失败恰好不被覆盖。

### 重做必须满足

- 用 **deployment checksum** 之类稳定标识判断回滚，不用 `ostree=` 原串；
- 故障注入的计时窗口必须对齐**被注入的真实阶段**，并先证明该窗口被正确测量；
- 预算数字要与 harness 内部 deadline **在同一处推导**，且有守卫断言；
- 健康检查必须区分"**服务失败**"与"**本机就没有该条件**"（离线、无显示器、CI）；
- 在强制验签存在**之前**，不要把 fail-closed 的悬空引用变成可写 tag。

## 4. OS 开发与游戏闭环（os-closed-loops）

**设计要点**：容器优先的开发闭环（首启离线编译验证）、游戏栈与 `vkcube`/`vulkaninfo` 验收。

### 致命

1. **新增文件不可解析**：给出的 `flathub.flatpakrepo` 用多行续行写 `Description`，
   **不是合法 GKeyFile**，且会让新加的守卫失败。
2. **rootless podman 很可能失败**：验收脚本经 `runuser -u ... env ...` 驱动，
   缺少 rootless podman 所需的会话/subuid 环境。
3. **超时预算自相矛盾**：把首启放宽 15 分钟，但 `test-install.sh` 的上层 deadline 未同步，
   GCP wrapper 完全未改。
4. **安全倒退**：预烘焙的 devbox 镜像 tag 硬编码，等于**镜像里多了一个永不打补丁的第二套 OS**，
   而设计把这种"陈旧性"当作可复现性的优点来论证。

### 重做必须满足

- 任何新增配置文件必须先确认**格式合法**（本仓库已有守卫会因此失败）；
- 在 `runuser` 环境下驱动 rootless 容器前，先证明 subuid/session 条件成立；
- 超时改动必须**同时**覆盖 unit、`test-install.sh` 与 GCP wrapper；
- 开发容器要有**更新路径**，不能把"永不变化"当卖点。

## 5. 跨四份设计的共性教训

1. **先核对现状再论证取舍。** 两份设计的核心论证建立在错误事实上
   （依赖已存在、能力已实现）。
2. **"默认关闭"必须真的能关闭。** 镜像只有一条无条件 `COPY`，
   "用 build ARG 排除子路径"在此仓库不成立。
3. **fail-open 最容易伪装成新功能。** 撤销列表、`required: false`、软跳过的 `if [ -f ]`
   都是"加了一个安全特性"，实则放宽。
4. **计时/预算必须与被测对象在同一处推导。** 三份设计各自出现预算矛盾。
5. **健康判定必须区分"坏了"与"这台机器本来就没有"。** 否则离线、无头、CI 场景被判红。
6. **安全能力要问"哪个入口真的调用它"。** 这正是本轮在 HCM 上发现的问题
   （库已验签、CLI 未接线），设计里又以另一种形式重现。

## 6. 本轮实际落地的部分

四份设计均未实现。但对抗复核**顺带发现了一处当前代码的真实缺陷**并已修复：

- **capability 列表无界**（actions 有上界、capabilities 没有），
  每次策略评估全量扫描、每次写入全量 fsync → 本地放大。
  已按"总量上界"（而非单请求上界）修复并加回归测试。

## 7. 下一轮建议顺序

1. **capability-auth**：方向已获认可，按 §1 的约束重做即可，是 executor 的阻塞前置项；
2. **os-reliability**：拆成三个独立小改动（digest 固定 / CI 预算与 `/dev/kvm` 断言 /
   greenboot），**不要一次性提交**——本轮正是因为耦合而同时踩中多条；
3. **hcm-v3**：先只做 `degraded`/`unknown` 证据词汇（最小、无签名影响），
   撤销与 cohort 选择器另议；
4. **os-closed-loops**：先做**开发闭环**（可在 CI 内验证），
   游戏闭环在没有真实 GPU 的 CI 里能证明的东西非常有限，优先级应低于其余三项。
